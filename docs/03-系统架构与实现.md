> V2 重构版的应用分层、调用链与关键实现
>
> 文档版本：V2 ｜ 落款：Zero

---

## 一、整体架构

```
┌─────────────────────────────────────────────┐
│  ui/        Streamlit 页面与组件             │  只调 service，不写 SQL
├─────────────────────────────────────────────┤
│  service/   用例编排、输入校验、结果封装     │  返回 OperationResult
├─────────────────────────────────────────────┤
│  repository/  SQL → DataFrame / 主键         │  不含业务判断
├─────────────────────────────────────────────┤
│  db/        连接池、参数化、过程调用、异常   │  唯一接触驱动的一层
├─────────────────────────────────────────────┤
│  SQL Server  表 / 视图 / 存储过程 / 触发器   │  业务不变式的最终防线
└─────────────────────────────────────────────┘
```

依赖方向严格单向：`ui → service → repository → db`。

- UI 不认识 SQL，repository 不认识 Streamlit
- service 是纯 Python，可脱离界面测试
- 换 Web 框架时，service 与 repository 可原样复用

## 二、各层职责

### 2.1 config

`warehouse/config.py` 是连接参数与业务阈值的唯一来源：

- 数据库：服务器、库名、账号、驱动
- 连接池：大小、溢出、回收、探活
- 业务：安全库存、预警页大小

优先级为**环境变量 > 默认值**。默认值保持通用（`localhost` + Windows 集成认证），仓库内不保存真实凭据。

`odbc_connection_string()` 负责拼接连接串；有用户名时走 SQL 身份验证，否则追加 `Trusted_Connection=yes`。`TrustServerCertificate=yes` 是为了兼容 Express 的自签证书。

### 2.2 db

**engine.py**

| 方法 | 用途 |
|---|---|
| `fetch_df(sql, params)` | 查询返回 DataFrame |
| `fetch_one` / `fetch_scalar` | 单行 / 单值 |
| `execute(sql, params)` | 写操作，返回受影响行数 |
| `call_procedure(name, args)` | 按名调用存储过程，处理 OUTPUT 参数 |

实现要点：

- 连接池由 SQLAlchemy 管理，`pool_pre_ping` 处理被服务端断开的死连接
- 所有 SQL 使用 `:name` 占位符，禁止 f-string 拼接
- 存储过程名无法参数化，因此维护 `ALLOWED_PROCEDURES` 白名单，同时声明输出参数类型
- 输出参数采用"先 DECLARE 局部变量 → EXEC ... OUTPUT → SELECT 回来"的方式，比依赖 pyodbc 的输出绑定稳定

**errors.py**

把驱动异常翻译为领域异常，是应用与数据库之间唯一的耦合点：

| 异常 | 触发场景 |
|---|---|
| `ValidationError` | 入参不合法（50006） |
| `NotFoundError` | 单据 / 行不存在（50001） |
| `PermissionDeniedError` | 无仓库权限或已离职（50003） |
| `StockShortageError` | 库存不足（50004） |
| `CapacityExceededError` | 库容不足（50005） |
| `DuplicateError` | 唯一约束（2627 / 2601） |
| `ReferenceError_` | 外键仍被引用（547） |

错误号来自存储过程的 `THROW` 或 SQL Server 原生错误码，映射集中在一处。UI 不需要解析驱动错误文本。

### 2.3 repository

只负责"把 SQL 变成数据对象"，不做业务判断。

| 模块 | 内容 |
|---|---|
| `master.py` | 工厂、供应商、仓库、库位、物品、员工与授权 |
| `stock.py` | 库存明细、预警、效期、周转、大屏维度、货位矩阵 |
| `operation.py` | 手工出入库、无单据调拨（调存储过程） |
| `orders.py` | 入库 / 出库 / 调拨 / 盘点单据的创建、查询、行操作 |
| `audit.py` | 流水、库存审计、权限审计、趋势 |

约定：

- 查询列一律起中文别名，界面不需要再做列名映射
- 列表查询带出后续操作需要的主键（如 `WarehouseID`、`ItemID`），避免界面靠名称反查
- `LIMIT` 用 `TOP` 下推到数据库，不把整表拉进内存再截断

### 2.4 service

用例编排层，统一返回：

```python
@dataclass
class OperationResult:
    ok: bool
    message: str
    record_id: int = 0
    group_id: str = ""
    detail: str = ""
    error: Exception | None = None
```

流程：

1. 校验必填项与数量范围（快速失败，不打扰数据库）
2. 必要时做一次预查询，让错误信息更具体（如"当前可用 12，本次申请 20"）
3. 调用 repository
4. 捕获 `DomainError`，转成 `OperationResult(ok=False, message=...)`
5. 非领域异常向上抛，由 UI 折叠进"技术细节"

**注意**：service 层的预查询只是提示，不是并发防护。真正的防护在存储过程的 `UPDLOCK + HOLDLOCK`。

### 2.5 ui

页面只调用 service，不直接访问 repository 或 engine。

| 模块 | 职责 |
|---|---|
| `theme.py` | 设计 token：颜色、圆角、阴影、图表模板、全局 CSS |
| `common.py` | 页头、指标卡、表格、图表、空状态、结果提示、删除确认 |
| `overview.py` | 库存总览（监控大屏） |
| `inbound.py` | 入库单创建、分批收货、历史查询 |
| `outbound.py` | 出库单创建、发货、历史查询 |
| `stocktake.py` | 盘点单生成、实盘录入、结案 |
| `operations.py` | 调拨单创建、发货、应急手工调拨 |
| `records.py` | 流水筛选与导出 |
| `master_data.py` | 主数据与库位维护 |
| `audit.py` | 库存 / 权限审计 |

## 三、一次收货的完整调用链

以"入库单分批收货"为例：

```
ui/inbound.py
  └─ 选择待收货单据 → 读明细 → 选择行、数量、货位、批次、效期
      └─ service/orders.receive(...)
          ├─ 校验必填项与数量
          └─ repository/orders.receive_line(...)
              └─ db/engine.call_procedure("sp_ReceiveInbound", [...])
                  └─ SQL Server
                      ├─ UPDLOCK 读取单据行与单头
                      ├─ 校验剩余待收、权限、货位归属、库容
                      ├─ INSERT Record（SourceType='入库单'）
                      ├─ TR_Record_StockSync
                      │   ├─ 按五元组合并/新增 Storage
                      │   └─ INSERT StockAudit
                      ├─ 回写行 ReceivedQty
                      └─ 推进单头状态（部分收货 / 已完成）
```

任何一步失败：

- 存储过程 `THROW` → `CATCH` 中 `ROLLBACK`
- 应用层 `errors.translate` 映射为领域异常
- service 返回 `OperationResult(ok=False, message=...)`
- UI 显示业务原因，不展示 SQL 栈

## 四、事务设计

### 4.1 为什么放在存储过程

| 方案 | 问题 |
|---|---|
| 应用层逐条执行 | 进程被终止时可能只完成一半；不同客户端各写一套顺序 |
| 应用层显式事务 | 仍依赖代码执行到底；跨语言客户端需重复实现 |
| 存储过程 | 由数据库引擎守护事务；任何客户端走同一套规则 |

### 4.2 事务内包含什么

以 `sp_ShipOutbound` 为例：

1. 锁读取出库单行与单头
2. 校验状态、剩余待发
3. 校验操作人权限
4. 锁读取可用库存并校验
5. 插入出库流水
6. 回写行 `PickedQty`
7. 推进单头状态

第 5 步的触发器在同一事务内扣减库存、写审计。任何一步失败，全部回滚。

### 4.3 不允许的操作

- 存储过程内不做长时间的外部调用
- 不在触发器里抛需要友好提示的业务错误
- 不把"查询展示"包进写事务，避免锁持有过久

## 五、并发控制

库存校验与扣减必须处于同一临界区：

```sql
SELECT @Available = ISNULL(SUM(Storing), 0)
FROM dbo.Storage WITH (UPDLOCK, HOLDLOCK)
WHERE ItemID = @ItemID AND WarehouseID = @WarehouseID;

IF @Available < @Qty
    THROW 50004, N'库存不足', 1;
```

- `UPDLOCK`：读取时取更新锁，阻止其他事务同时取得更新锁
- `HOLDLOCK`：等价 `SERIALIZABLE` 的范围锁，保持到事务结束
- 两者组合后，第二个并发请求会等待第一个提交，再基于新库存判断

代价是并发度下降。当前场景是本地单仓作业，正确性优先；高并发下可改为行级锁或乐观并发 + 重试。

## 六、异常处理

### 6.1 分层

| 层 | 处理方式 |
|---|---|
| 存储过程 | `THROW` 业务错误码；`XACT_ABORT ON` 自动回滚 |
| db/errors | 按错误号映射为领域异常 |
| service | 捕获领域异常 → `OperationResult` |
| ui | 业务失败显示红色提示；未知异常折叠进"技术细节" |

### 6.2 为什么不在 UI 解析错误文本

驱动错误信息是给 DBA 看的，包含表名、约束名、行号，用户无法理解，也可能泄漏结构。错误号映射集中在一处，修改提示文案不影响其他层。

## 七、界面实现

### 7.1 设计系统

`theme.py` 定义颜色、圆角、阴影与 Plotly 模板，页面只引用语义名：

```python
BRAND, SUCCESS, WARNING, DANGER, MUTED, INK, INK_2, LINE
```

CSS 只选择 `data-testid`，不碰 Streamlit 自动生成的 class 名，升级时不易整块失效。

`.streamlit/config.toml` 锁定浅色主题。设计 token 基于"浅底深字"，若不锁定，系统深色模式会把未被覆盖的文字翻成浅色，与自定义浅色背景冲突。

### 7.2 图表

- 统一走 `common.chart(fig)`，关闭 Plotly 工具栏（`displayModeBar: False`），避免悬停时遮住图形
- 所有图表共用配色与网格线
- 图表高度 ≥ 280、字号 ≥ 12，保证大屏可读

### 7.3 货位矩阵

一个格子一个货位：

- 色相表示主品类，明度表示占用量
- 只保留基色的色相与饱和度，明度按占用比例重算，保证不同品类可以横向比较
- 深灰表示空货位，无色表示该位置没有货位
- 用 `add_shape` 逐格绘制，透明散点承接悬停；Heatmap 的一维 colorscale 表达不了两个维度

### 7.4 交互

| 场景 | 处理 |
|---|---|
| 建单 | 物品下拉显示完整名称，逐行添加明细；避开空表 `data_editor` 下拉渲染内码的问题 |
| 数量 | 出库 / 调拨提供 25% / 50% / 全部快捷值 |
| 预判 | 入库显示剩余库容，出库显示可用量，调拨显示源库存与目标库容 |
| 反馈 | 成功用 toast，失败用内联提示；不因提示条挤压页面 |
| 删除 | 必须勾选确认，未选中时按钮置灰 |
| 空状态 | 给出下一步操作，而不是"暂无数据" |

## 八、可测试性

分层带来的直接收益：

- `tests/test_service.py` 不需要启动 Streamlit，直接调用 service 校验分支
- `tests/db_smoke.py` / `wms_smoke.py` 直接连数据库，验证约束、触发器、过程与回滚
- UI 页面可单独调用 `render()` 做渲染冒烟

如果所有逻辑都写在 `app.py` 里，以上测试都无法独立执行。

## 九、扩展方向

| 方向 | 做法 |
|---|---|
| REST API | service 层已是纯 Python 用例，套 FastAPI 暴露接口 |
