# 项目概述

> 智能仓库管理系统 ｜ 从课程设计到可运转的 WMS
>
> 文档版本：V2 ｜ 落款：Zero

---

## 一、项目背景

仓库管理的日常并不缺"记录"，缺的是**记录之间的因果关系**。

一张出库单发出去，库存要减少、批次要扣减、审计要留痕、单据状态要推进；如果这些动作分散在界面代码里逐条执行，任何一步失败都会留下半条数据。再往下追问：这批货是哪张采购单收的？客户订的 100 件还差多少没发？货放在哪个货位？哪一批先到期？——只靠一张库存表和一张流水表，答不上来。

本项目从一个课程设计出发，先实现一套能完成日常记账的库存系统（V1），再沿着上述问题做了一次完整重构（V2）：**补单据层、补库位层、补批次效期、把一致性交给数据库。**

---

## 二、项目定位

| 维度 | 说明 |
|---|---|
| 类型 | 数据库课程综合设计 → 工程化重构案例 |
| 业务范围 | 主数据、库存、入库、出库、调拨、盘点、审计、监控 |
| 技术形态 | 单体桌面 Web 应用（Streamlit），本地 SQL Server |
| 主要价值 | 展示数据库设计能力、业务建模能力、工程分层与质量意识 |
| 非目标 | 高并发生产部署、多租户 SaaS、移动端 |

项目刻意保持单体与本地部署，把复杂度集中在**数据模型与业务不变式**上，而不是分布式基础设施。

## 三、要解决的实际问题

### 3.1 业务问题

| 问题 | 现实影响 | V2 的处理 |
|---|---|---|
| 库存变动没有单据依据 | 事后无法解释"为什么少了 20 件" | 入库 / 出库 / 调拨 / 盘点全部单据化，流水带来源单据与行号 |
| 分批到货无法表达 | 采购 100 件先到 60，只能当两次无关入库 | 入库单支持部分收货，状态自动推进 |
| 客户订单进度不透明 | 不知道还差多少没发 | 出库单记录计划 / 已发 / 待发与进度 |
| 只到仓库层级 | 拣货员不知道去哪个货位 | 仓库 → 库区 → 货位三级，库存绑定货位 |
| 只按入库先后出库 | 临期货积压，过期报废 | 出库按 FEFO 自动选批 |
| 没有盘点流程 | 账实不符只能手工改数，无痕迹 | 盘点单带账面数，差异转盘盈 / 盘亏流水 |
| 跨仓调拨易丢失 | 货扣了但目标仓没入账 | 一张调拨单约束两端，发货生成同组双流水 |
| 库存预警口径错误 | 同一物品多个供应商批次重复报警 | 安全库存按"物品 × 仓库"聚合 |

### 3.2 工程问题

| 问题 | V2 的处理 |
|---|---|
| SQL 拼接 | 全参数化，存储过程调用走白名单 |
| 事务边界不清 | 核心作业封装为存储过程，单事务提交或整体回滚 |
| 并发超卖 | `UPDLOCK + HOLDLOCK` 圈定读-判-写临界区 |
| 异常不可读 | 驱动错误统一映射为领域异常，界面只展示业务原因 |
| 无测试 | 40 项自动化测试，覆盖约束、过程、作业链路与应用校验 |
| 界面与业务耦合 | `ui → service → repository → db` 单向依赖 |

## 五、成果概览

### 5.1 规模

| 指标 | V1 | V2 |
|---|---|---|
| Python | 约 750 行（单文件） | 约 4,800 行（5 层 + 测试） |
| SQL | 约 550 行 | 约 2,500 行 |
| 表 | 9 | 22 |
| 视图 | 0 | 13 |
| 存储过程 | 0 | 7 |
| 触发器 | 3 | 3 |
| 页面 | 5 | 8 |
| 自动化测试 | 0 | 40 |

### 5.2 关键结果

- 核心作业（收货、发货、调拨、盘点结案）全部由存储过程完成，单据、流水、库存、审计在同一事务内一致
- 出库从"按供应商排序"改为 FEFO，临期批次优先出
- 仓库使用量由触发器维护，恒等于库存之和，不再出现建库假值
- 库存查询统一走视图，供应商为空的批次不再被隐藏
- 安全库存预警从按批次改为按"物品 × 仓库"，消除重复报警
- 40 项测试通过，8 个页面渲染无异常

## 六、简历表述（可直接摘用）

> **智能仓库管理系统｜SQL Server + Python / Streamlit**
>
> 独立完成从课程设计到 WMS 的数据库重构：设计 22 张表达 3NF 的表，覆盖主数据、库位、批次效期、四类作业单据与双表审计；用 13 个视图统一查询口径，7 个存储过程封装收货、发货、调拨、盘点的事务边界；通过 `UPDLOCK/HOLDLOCK` 解决库存校验与扣减之间的超卖窗口；出库实现 FEFO（先到期先出）。
>
> 应用侧按 `config / db / repository / service / ui` 五层解耦，全参数化查询；配套 40 项自动化测试与监控大屏，8 个页面全部通过渲染验证。

### 可展开讲的技术点

1. **为什么把事务放进存储过程**：进程可能被终止，应用层事务依赖代码执行到底；数据库守护事务，也统一多客户端规则
2. **FEFO 与 FIFO 的差别**：食品、医药、化工的效期是硬约束，只按入库先后出会让临期货积压
3. **单据层的价值**：库存变动从"一条流水"变成"一张单的多次执行"，才能回答进度、差异与追溯
4. **审计表拆分**：一个字段只表达一个语义，避免 `OldQuantity` 有时存数量、有时存 StaffID
5. **视图作为口径层**：同一份库存，库存页、预警、大屏、导出必须用同一套 JOIN，否则数字对不上

## 七、范围与边界

**已实现**：主数据、库存、入库、出库、调拨、盘点、批次效期、库位、审计、监控大屏、权限（员工 × 仓库）。

**有意未做**：

- 波次拣货与拣货路径优化（需要更复杂的任务分配状态机）
- 质检隔离流程（待检区 → 合格转存储区）已建库区，但未实现流转
- 每日库存快照（当前趋势看流水，不做近似反推）
- 高并发压测与生产级部署

这些边界写在文档里，是为了说明"没做"是范围选择，而不是遗漏。
