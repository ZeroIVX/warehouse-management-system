# 版本差异与迁移说明

> V1 原始版 → V2 重构版：改了什么、为什么改、怎么迁移
>
> 文档版本：V2 ｜ 落款：Zero

---

## 一、两版定位

| | V1 原始版 | V2 重构版 |
|---|---|---|
| 目录 | `v1-legacy/` | `v2-wms/` |
| 形态 | 单文件 Streamlit，约 750 行 | 5 层应用，约 4,800 行 Python |
| 数据库 | 9 表 / 0 视图 / 0 过程 / 3 触发器 | 22 表 / 13 视图 / 7 过程 / 3 触发器 / 13 索引 |
| 业务 | 手工出入库、调拨、查询、审计 | 单据化入库 / 出库 / 调拨 / 盘点、库位、批次效期、FEFO |
| 用途 | 对照、追溯 | 主要交付、可运行 WMS |

V1 不是"失败版本"，它完成了从 0 到 1：把业务跑通、把数据落库。V2 解决的是从 1 到可用：让数据经得起追问。

## 二、V1 的问题与 V2 的处理

### 2.1 正确性

| 问题 | V1 写法 | 后果 | V2 处理 |
|---|---|---|---|
| 触发器只处理首行 | `SELECT @ItemID = ItemID, @Qty = OperationQuantity FROM inserted` | 批量插入时只有最后一行生效，其余静默丢失 | 游标遍历 `inserted`，与行数无关 |
| 出库顺序错误 | 按 `SupplierID` 排序扣减 | 与"先进先出"无关，批次扣减不可解释 | 按 `StorageID` / 效期排序，升级为 FEFO |
| 库存隐藏 | 库存页 `INNER JOIN Supplier` | 供应商为空的批次整行消失（实测 104 件） | 统一走 `vw_StockOverview`，`LEFT JOIN` |
| 使用量失真 | `WarehouseUsage` 无维护逻辑 | 建库后一直是假值（如 3200，实为 418） | 独立触发器同步 + `CHECK (Usage <= Size)` |
| 预警重复 | 按供应商批次判断安全库存 | 同一物品三个供应商各 15 件会报三次缺货 | 按"物品 × 仓库"聚合 |

### 2.2 并发

| 问题 | 说明 | V2 处理 |
|---|---|---|
| 超卖窗口 | 库存校验在 `SELECT`，扣减在触发器，两者之间无锁 | 读取待发 / 库存 / 库容统一 `UPDLOCK + HOLDLOCK`，圈进同一事务 |
| 部分提交 | 多条语句逐条执行，中途失败留下半条数据 | 核心作业封装为存储过程，`XACT_ABORT ON` + `TRY/CATCH` 整体回滚 |
| 调拨单边 | 两条流水分别插入，第二条失败则源仓已扣 | `sp_TransferStock` / `sp_ShipTransfer` 同一事务内写两条同组流水 |

### 2.3 数据建模

| 问题 | V1 | V2 |
|---|---|---|
| 审计表一表两用 | `AuditLog.OldQuantity` 存过数量，也存过 `StaffID`；`NewQuantity` 存过 `WarehouseID` | 拆 `StockAudit` / `PermissionAudit`，字段语义唯一 |
| 调拨靠文本 | `Remarks` 写 `'调拨-发货'` 区分方向 | `OperationType` 增加受约束的 `调拨入 / 调拨出`，用 `TransferGroupID` 成组追溯 |
| 仓库类型自由文本 | 前端硬编码三个选项，库里实际五类，新增类型要改代码 | `WarehouseType` 字典表，前端由字典驱动 |
| 无单据层 | 一条流水就是一次动作，无法表达"计划 100、已收 60" | 四类单据 + 明细行 + 状态机 |
| 无库位 | 库存只到仓库 | 仓库 → 库区 → 货位三级 |
| 无批次效期 | 库存按"物品 + 仓库 + 供应商" | 五元组唯一键，增加批次、生产 / 失效日期 |

### 2.4 安全

| 问题 | V1 | V2 |
|---|---|---|
| SQL 拼接 | 6 处 f-string 拼 SQL | 全参数化；存储过程名走白名单 |
| 凭据硬编码 | 连接串写在 `get_connection()` 内 | 环境变量 / `db.env`，默认 Windows 集成认证 |
| 异常吞掉 | 多处裸 `except` 返回空字典 | 统一翻译为领域异常，未知异常显式上报 |

### 2.5 可维护性

| 问题 | V1 | V2 |
|---|---|---|
| 单文件 | UI / SQL / 业务混写 | `config / db / repository / service / ui` 五层 |
| 连接管理 | 每个函数新建连接、关闭 | SQLAlchemy 连接池 + `pool_pre_ping` |
| 列名重复 | 每个页面自己写 JOIN 与别名 | repository 统一中文别名，视图统一口径 |
| 空值处理 | `None` 直接进表格 | 明确空状态与数值转换 |

### 2.6 可测试性

| | V1 | V2 |
|---|---|---|
| 自动化测试 | 0 | 40 项（数据库 26 + 应用 14） |
| 页面验证 | 手工点 | 8 个页面渲染冒烟 + 浏览器截图核对 |

## 三、重构路径

V2 不是一次性重写，而是按依赖顺序推进：

```
1. 先修数据模型
   ├─ 拆审计表
   ├─ 抽仓库类型字典
   ├─ 增加批次 / 货位 / 效期
   └─ 建立四类单据表
        ↓
2. 再修数据一致性
   ├─ 重写触发器（多行安全、FEFO、使用量同步）
   ├─ 新增存储过程（收货 / 发货 / 调拨 / 盘点）
   └─ 增加约束、索引、视图
        ↓
3. 再做应用分层
   ├─ config / db / repository / service / ui
   ├─ 全参数化 + 异常映射
   └─ 统一返回 OperationResult
        ↓
4. 最后做界面与验证
   ├─ 设计系统、监控大屏、货位矩阵
   ├─ 40 项自动化测试
   └─ 8 个页面渲染与截图核对
```

顺序不能反：如果先写界面再改表，所有页面都要重做；先把数据模型和事务定下来，上层才有稳定契约。

## 四、数据迁移

V1 → V2 的数据迁移不是简单 `INSERT SELECT`，有三个必须处理的点：

1. **仓库类型映射**：V1 存中文字符串（常温库 / 冷链库 / 恒温库 / 危化库 / 特种库），V2 存字典表外键，需要先建字典再映射
2. **库存拆分**：V1 的 `Storage` 没有批次与货位，迁移时补默认批次号，再按仓库分配到存储区货位
3. **流水触发器**：直接灌 `Record` 会再次扣减库存并重复写审计，导入期间必须禁用 `TR_Record_StockSync`，灌完恢复

归档版的做法：

- `v2-wms/sql/06_seed.sql` 提供**自包含**的初始化数据，不依赖 V1 数据库
- `07_demo_data.sql` 通过 `sp_PostOperation` 生成演示流水，而不是直接插 `Record`，保证库存、审计、流水自洽
- `08_demo_orders.sql` 通过存储过程创建三种状态的单据与一张进行中的盘点单

## 五、V1 归档时改了什么

只改三处，均为可运行性与脱敏需要：

1. 连接参数从硬编码改为 `WAREHOUSE_DB_*` 环境变量，默认 Windows 集成认证
2. 建库脚本库名由 `WarehouseDB` 改为 `WarehouseDB_V1`，避免与 V2 冲突
3. `Styler.applymap` 增加兼容分支（pandas 3 已移除该方法），优先 `Styler.map`，
   旧版本回退，展示效果不变

业务逻辑、SQL 写法、界面结构保持原样，方便对照。V1 的已知问题在 `v1-legacy/README.md` 中逐条列出，未做"顺手修复"。

## 七、没有做的事

以下差异是**范围选择**，不是遗漏：

- 质检流转：已建"待检区"库区，但"待检 → 合格转存储"的状态机未实现
- 波次拣货：多张出库单合并拣货路径，需要任务分配与路径优化
- 每日库存快照：当前趋势看流水，不做近似反推
- 生产级并发：本地单仓场景，正确性优先于吞吐
